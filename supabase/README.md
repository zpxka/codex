# Supabase 공용 데이터베이스 설정

현재 저장소에는 연동 코드와 SQL·테스트가 준비되어 있습니다. 아래는 최초 설정 절차이며 이미 운영 프로젝트 연결·자료 이전을 마쳤다면 프로젝트/SQL을 다시 생성하지 마세요. 개발 환경에는 실제 접속 정보가 없어 실접속 자동 검증은 미실행입니다. 자동 테스트에는 운영 프로젝트와 다른 전용 프로젝트를 사용합니다([테스트 사용법](TESTING.md)). 화면 명칭은 Supabase 서비스 개편에 따라 조금 달라질 수 있습니다.

## 1. 사용자가 프로젝트를 만들기

1. Supabase 계정을 만들고 대시보드에서 **New project**를 선택합니다.
2. 연구팀용 프로젝트를 만들고 가까운 리전을 고릅니다. DB 비밀번호는 비밀번호 관리자에 보관합니다. ReviewLab 앱에는 DB 비밀번호나 직접 연결 문자열을 넣지 않습니다.
3. 프로젝트가 준비되면 **SQL Editor → New query**에서 [202610240001_shared_storage.sql](migrations/202610240001_shared_storage.sql) 전체를 실행합니다. 프로젝트 소유자/관리자가 **한 번** 적용하는 파일입니다. 실제 데이터가 있는 기존 프로젝트에 임의의 DROP/초기화 SQL을 실행하지 마세요.
4. SQL Editor에서 `select version, applied_at from reviewlab.schema_migrations;`로 버전 1을 확인합니다. 이 스키마는 SQLite의 스키마 1·2와 별도 관리됩니다.
5. 프로젝트 설정의 **API / Data API / Connect** 영역에서 **Project URL**과 **Publishable key**를 찾습니다. 기존 프로젝트라면 **legacy anon key**도 지원합니다. `service_role`, `sb_secret_...`, DB 연결 문자열은 앱에서 사용하지 않습니다. 실제 키를 GitHub나 채팅에 올리지 마세요.

이 SQL은 `reviewlab` 스키마에 정규 테이블을 만들고 `public`에는 제한된 RPC 함수만 만듭니다. Data API에는 `public`만 노출하는 기본 구성을 유지하세요. `reviewlab` 스키마를 공개 API 노출 목록에 추가할 필요가 없습니다. 테이블을 만들면서 자동 생성되는 공개 읽기 정책을 별도로 추가하지 마세요.

## 2. 로그인 계정과 권한

1. **Authentication → Providers / Sign In**에서 이메일·비밀번호 로그인을 사용합니다.
2. 공개 회원가입 허용을 끄고, **Authentication → Users**에서 연구팀 사용자만 생성하거나 초대합니다. 초대를 이용하면 이메일의 링크에서 이메일 확인·비밀번호 설정을 완료합니다. 앱 안에는 회원가입·관리자 계정 생성 기능이 없습니다.
3. 노트북과 데스크탑을 쓰는 한 사람은 두 기기에서 같은 계정으로 로그인해도 됩니다. 팀원은 각자의 계정을 사용하세요.
4. 첫 사용자는 ReviewLab에서 로그인한 뒤 왼쪽 **새 공용 작업공간 만들기**에서 연구팀 작업공간을 하나 만듭니다. 생성자는 `owner` 구성원이 됩니다. 새 작업공간의 태그는 로컬 자료를 이전하거나 CSV 등록/태그 관리로 채울 수 있습니다.
5. 팀원을 추가할 때 프로젝트 관리자가 SQL Editor에서 아래 형식으로 실제 UUID를 입력합니다. 작업공간 ID는 앱의 **공용 DB 관리**, 사용자 ID는 **Authentication → Users**에서 확인합니다.

```sql
-- 문자열은 각각 실제 UUID로 바꿉니다. 이메일이나 비밀번호를 넣지 않습니다.
insert into reviewlab.workspace_members (workspace_id, user_id, role)
values ('<작업공간 UUID>'::uuid, '<팀원 Auth 사용자 UUID>'::uuid, 'editor')
on conflict (workspace_id, user_id) do update set role = excluded.role;
```

`<...>`는 설명용 자리표시자이며 그대로 실행하면 오류가 납니다. 두 기기에서 각각 같은 이름의 작업공간을 새로 만들면 서로 다른 DB 영역을 보게 됩니다. 반드시 **같은 작업공간 ID**를 선택하세요.

권한을 철회하려면 관리자가 해당 구성원 행을 삭제합니다. 이후 서버 읽기·쓰기 요청은 즉시 거부됩니다. 이미 내려받은 파일·백업은 별도로 관리해야 합니다. Auth 사용자만 삭제하려 할 때 FK 오류가 나면 먼저 해당 사용자의 구성원 행을 관리자가 검토·정리하세요. 팀 작업공간과 연구자료를 함께 삭제할 필요는 없습니다.

RLS는 인증된 구성원에게만 해당 작업공간의 읽기를 허용합니다. 앱 사용자는 테이블 직접 INSERT/UPDATE/DELETE 권한이 없고 인증 검사·버전 검사 RPC로만 씁니다. RPC는 고정 `search_path`와 `auth.uid()` 회원 검사를 사용하는 SECURITY DEFINER입니다. 테이블 소유자(배포 관리자)의 권한으로 트랜잭션을 수행하므로 소유자에게 FORCE RLS를 적용하지 않으며, 일반 사용자에게는 RLS가 적용됩니다. 프로젝트 관리자·DB 소유자는 관리 권한을 가지므로 그 계정을 앱용으로 공유하지 마세요.

## 3. Windows 노트북과 데스크탑 설정

**각 기기에서** 아래 작업을 반복합니다.

1. GitHub 최신 ZIP을 받고 모두 압축 해제합니다. 기존 앱이 실행 중이면 터미널에서 `Ctrl+C`로 종료합니다.
2. `app.py`가 들어 있는 폴더의 `.streamlit`에서 `secrets.toml.example`을 **`secrets.toml`**로 복사합니다. Windows가 확장자를 숨기면 `secrets.toml.txt`로 저장되지 않았는지 확인하세요. 기존 secrets가 있다면 덮어쓰지 말고 `[reviewlab]` 항목을 추가합니다.
3. 메모장으로 아래 두 값만 실제 프로젝트에서 복사해 넣습니다.

```toml
[reviewlab]
storage = "local"
supabase_url = "" # 여기에 실제 HTTPS Project URL
supabase_key = "" # 여기에 실제 publishable 또는 anon key
```

4. `Start_ReviewLab.cmd`를 더블클릭합니다. 기존과 같이 패키지 설치 후 `http://127.0.0.1:8501`에서 열립니다. 관리자 권한·방화벽·프록시 변경은 필요하지 않습니다.
5. 왼쪽 **저장소 → Supabase 공용 저장소**를 선택하고 Supabase 계정 이메일·비밀번호로 로그인합니다.
6. 첫 기기에서 만든 **같은 공용 작업공간**을 두 기기에서 선택합니다. **실제 연구자료 / 예시·연습 자료** 선택도 일치해야 합니다.
7. 처음에는 **예시·연습 자료**에서 가상 테스트 자료만 등록·수정하여 아래 점검을 수행합니다. 완료 후 실제 모드로 전환하고 노트북의 실제 SQLite를 이전합니다.
8. 공용 모드를 기본으로 쓰려면 테스트가 끝난 뒤 `storage = "supabase"`로 바꿉니다. 로컬 파일을 없애는 설정은 아닙니다.

PowerShell을 직접 사용할 때는 가상환경 활성화 없이 실행할 수 있습니다.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

secrets 대신 환경변수를 쓸 수도 있습니다. 다음 값은 프로젝트에서 복사하고 빈칸 예시를 실제 연결 성공으로 간주하지 마세요.

```powershell
$env:REVIEWLAB_SUPABASE_URL = "프로젝트에서 복사한 HTTPS URL"
$env:REVIEWLAB_SUPABASE_KEY = "프로젝트에서 복사한 publishable 또는 anon key"
$env:REVIEWLAB_STORAGE = "supabase"
.\.venv\Scripts\python.exe -m streamlit run app.py
```

계정 비밀번호는 앱 로그인 화면에서 입력합니다. 명령줄·Git·설정 예제에 비밀번호를 넣지 않습니다. 환경변수는 현재 PowerShell 창에 적용되므로 다른 창/더블클릭 실행에도 적용하려면 각 실행 환경에 설정하거나 secrets를 쓰세요. `.env.example`은 항목 설명용이며 앱이 `.env`를 자동으로 읽지는 않습니다. GitHub ZIP을 새 폴더에 받으면 실제 `secrets.toml`은 포함되지 않으므로 직접 안전하게 복사해야 합니다.

## 4. 데이터가 보이는 시점과 충돌

- 공용 저장이 성공하면 PostgreSQL에 바로 반영됩니다. 읽기 전용 메인 대시보드는 약 10초마다 변경을 확인하고 새로 불러옵니다.
- 입력·수정·리뷰 분석 화면은 작성 중인 값을 보호하기 위해 알림만 띄웁니다. **공용 자료 새로고침**을 누르면 최신 자료를 다시 읽습니다. 참고문헌 수정 폼의 값도 최신 데이터로 교체되므로 미저장 입력은 먼저 복사하세요.
- 현재 버전 검사는 **작업공간 + 실제/예시 모드 전체** 단위입니다. 같은 자료뿐 아니라 서로 다른 자료를 동시에 바꿔도 충돌할 수 있습니다. 먼저 저장한 요청만 성공하고, 다른 요청은 중단됩니다. 새로고침 후 자신의 변경을 다시 검토하여 저장하세요.
- 저장 결과를 확인할 수 없으면 성공 안내를 하지 않습니다. 입력 후보 전체를 이 기기의 `cloud/.../pending/`에 SQLite와 요청 메타데이터로 보존합니다. 복구 사본에는 키·비밀번호·로그인 토큰을 넣지 않습니다.
- 인터넷 복구 후 **공용 DB 관리 → 미확인 저장 요청 → 같은 요청 결과 확인·재시도**를 사용합니다. 서버가 이미 저장한 요청이면 요청 ID로 결과만 돌려주고 다시 적용하지 않습니다. 그 뒤 다른 기기가 저장한 변경도 되돌리지 않습니다. 실제 충돌이면 사본을 내려받아 내용을 확인하고 최신 자료에 필요한 변경만 수동으로 반영하세요.
- 서버가 확인되지 않은 후보 사본은 정상 자동 백업을 덮어쓰지 않습니다. 공용 연결 실패 시 자동으로 로컬 모드에 저장하는 동작도 없습니다.

로그인 토큰은 사용자 Streamlit 세션 메모리에만 보관하고 공유 캐시에 넣지 않습니다. 자동 갱신이 실패하거나 브라우저 세션이 종료되면 다시 로그인해야 할 수 있습니다. **공용 저장소 로그아웃**은 현재 기기의 인증 세션을 종료합니다. 로컬 백업·복구 사본은 보존되므로 자신의 Windows 계정과 저장 폴더 접근 권한을 보호하세요.

## 5. 기존 노트북 SQLite 이전

1. 노트북의 기존 앱에서 **설정 및 데이터 관리 → 로컬 저장 위치**를 확인합니다. 기본값은 `%USERPROFILE%\.reviewlab\actual\reviewlab.sqlite3`이고 예시는 `example` 폴더입니다. 사용자 지정 `REVIEWLAB_DATA_DIR`이 있다면 그 경로를 사용합니다.
2. 가능하면 이전 중에는 다른 기기의 편집을 잠시 멈춥니다. 원본 앱을 반드시 삭제하거나 원본 DB를 교체할 필요는 없습니다.
3. Supabase 공용 모드에서 올바른 작업공간·실제/예시 모드를 선택하고 **공용 DB 관리**를 엽니다.
4. **이 컴퓨터의 기존 SQLite**에서 원본 파일 경로를 확인하고 **이전 전 백업 만들기·미리보기**를 누릅니다. 읽기 전용 SQLite 백업 API로 `backups/before-cloud-<UUID>.sqlite3`를 만든 뒤 사본을 검사합니다. 원본에는 쓰지 않습니다. SQLite 스키마 1 또는 2를 지원합니다.
5. 참고문헌·태그·검증 이력·리뷰 프로젝트·리뷰 원본·메모·검토·참고문헌 연결·분석 실행별 추가/동일 ID 건수를 확인합니다.
6. 서로 다른 ID의 중복 후보는 자동 삭제·병합하지 않습니다. 목록을 검토하고 **모두 별도 자료로 보존**할 때만 확인합니다. 같은 이름 태그를 기존 ID에 연결할 경우 별도 확인이 필요합니다. 재사용한 태그 ID를 제외한 자료·이력 UUID와 원문·시각은 보존합니다.
7. 같은 ID의 내용·태그·검증 이력·프로젝트 내용이 다르면 전체 이전을 차단합니다. 새 ID를 임의로 만들거나 기존 레코드를 덮어쓰지 않습니다. 별도의 빈 작업공간에 이전하거나 차이를 먼저 검토하세요.
8. 백업과 과거 검증/검토 이력 승계에 체크하고 **공용 DB로 추가 이전 실행**을 누릅니다. 이전은 단일 서버 트랜잭션이며 실패해도 원본과 사전 백업은 유지됩니다. 미리보기 이후 다른 저장이 있으면 충돌로 중단합니다.
9. 두 번째 기기에서 같은 작업공간을 열고 **공용 자료 새로고침**으로 제목·태그·검증·리뷰 건수를 확인합니다. 이전 직후에는 원본 SQLite와 전체 백업을 별도 보관하세요.

개별 자료의 검증/검토 이력 순서는 유지하며 내부 전역 sequence 번호는 대상의 기존 번호 뒤로 배치될 수 있습니다. 이미 완전히 같은 ID·내용·이력이 있으면 건너뜁니다. 로컬과 공용을 동시에 계속 편집하면 자동 양방향 병합되지 않습니다. 공용 전환 이후에는 두 기기에서 공용 모드로 작업하는 것을 권장합니다.

## 6. 백업과 복구

- **자동:** 공용 자료를 읽거나 서버 저장을 확인한 후, 해당 기기의 사용자 데이터 폴더 `cloud/<프로젝트 식별자>/<작업공간 ID>/<모드>/backups/automatic/`에 날짜별 최신 SQLite를 보관합니다. 최근 30개 UTC 날짜의 사본만 유지하며 수동·이전 전·미확인 사본은 자동 삭제하지 않습니다. 앱이 꺼져 있으면 이 기기의 사본 갱신도 멈춥니다.
- **서버 측:** Supabase 대시보드의 Database Backups/PITR에서 현재 플랜의 제공 범위·보존 기간·복구 방법을 확인하세요. 플랜에 따라 다르며, 이 코드가 Supabase 서버 백업이나 PITR를 자동 활성화하지는 않습니다. 앱을 열지 않아도 보관되는 서버 백업이 필요한 경우 관리자가 해당 기능을 설정해야 합니다.
- **수동 전체 백업:** 공용 DB 관리에서 **전체 SQLite 백업 만들기 → 다운로드**를 이용합니다. 두 단계의 자료·검증/검토·분석 기록 전체가 들어 있습니다. 로그인 토큰·키는 포함하지 않습니다.
- **기존 CSV:** 참고문헌 전용 CSV와 리뷰 프로젝트 전용 CSV의 내보내기/추가 복원 기능도 유지됩니다. 각각의 범위만 담으므로 전체 백업과 혼동하지 마세요.
- **공용 추가 복원:** 공용 DB 관리에서 **전체 SQLite 백업 파일 업로드**를 선택하고 이전과 같은 미리보기·중복 확인 절차를 밟습니다. 기존 공용 DB를 통째로 덮어쓰지 않습니다. 백업 시점 그대로 검증하려면 별도의 빈 작업공간을 만드세요.
- **로컬로 복구:** 앱을 종료하고 백업을 **새 데이터 루트/같은 모드/reviewlab.sqlite3**로 복사한 뒤 `REVIEWLAB_DATA_DIR`을 새 루트로 설정하여 로컬 SQLite 모드로 실행합니다. 실행 중인 원본이나 유일한 백업을 교체하지 마세요.

백업 파일은 암호화된 형식이 아닙니다. OS 권한으로 보호하고 연구팀이 승인한 별도 저장장치에도 보관하세요. 한 기기에서 확인하지 않은 다른 기기의 최신 버전은 그 기기의 로컬 자동 사본에 없을 수 있으므로 서버 백업과 수동 전체 백업도 함께 사용합니다.

개발용 대화형 백업 명령도 제공합니다. 환경변수로 URL·publishable key를 설정한 뒤 실행하면 이메일·비밀번호를 입력받습니다. 비밀번호는 파일이나 명령줄에 저장하지 않습니다.

```powershell
.\.venv\Scripts\python.exe scripts\cloud_backup.py --workspace "실제 작업공간 UUID" --mode actual --output-root "$env:USERPROFILE\ReviewLabBackups"
```

## 7. 실제 자료 전환 전 점검표

이 저장소의 자동 테스트와 별개로 **사용자의 실제 Supabase 프로젝트에서** 아래를 확인해야 합니다. 아직 수행했다고 보고하지 않습니다.

- 예시 모드에서 가상 자료 등록 → 다른 기기 새로고침 → 같은 제목·태그·검증 이력 확인
- 두 기기에서 같은 자료를 열고 먼저 A 저장, 오래된 B 저장 → 충돌 안내와 A 내용 유지
- 공용 모드의 일반 참고문헌 CSV 등록 및 리뷰 업로드/검토/CSV 내보내기 확인
- 작업공간에 추가하지 않은 별도 테스트 계정은 팀 자료를 읽지 못하는지 확인
- 인증 없이 Data API/RPC를 호출하면 보호되는지, service_role이 앱 설정에 없는지 확인
- 테스트 SQLite 이전 후 원본 파일과 공용 자료·이력 건수 비교
- 네트워크 단절 후 성공 안내가 나오지 않는지, 복구 요청 재확인 뒤 중복 저장이 없는지 확인
- 전체 백업을 별도 테스트 작업공간 또는 새 로컬 경로에 복원해 한글·이력·리뷰를 확인

## 8. 한계 및 향후 확장

현재 공용 어댑터는 한 사용자 세션의 SQLite 작업 사본을 기존 서비스에 제공하고, 공용 PostgreSQL의 11개 정규 테이블과 버전 검사 RPC로 교환합니다. 하나의 JSON 컬럼에 DB 전체를 보관하는 구조가 아닙니다. 키는 `(작업공간, 모드, 원래 ID)`이며 연결 FK에도 작업공간·모드가 포함됩니다.

소규모 연구팀용 첫 버전으로 공용 모드별 데이터는 **20MB·50,000개 레코드(자료·연결·이력 포함)**로 제한합니다. 리뷰 프로젝트 5,000리뷰·CSV 제한도 그대로 적용됩니다. 전송/검사 비용과 보수적인 충돌 범위 때문에 대규모 데이터·동시 다수 사용자 작업에는 행 단위 변경 RPC로 개선해야 합니다.

3~5단계는 아직 구현하지 않았습니다. 새 테이블은 독립 `survey_*`, `document_*`, `ai_*`, `submission_*` 이름으로 추가하고 작업공간·모드 FK, RLS, 백업, 버전 마이그레이션을 함께 확장해야 합니다. Supabase SQL v2와 클라이언트 지원 버전 확인 없이 테이블을 임의로 추가/변경하지 마세요.

## Windows에서 ‘서버 전송 전’ 오류가 난 경우

복구 사본을 만드는 코드에서 `with sqlite3.connect(...)`가 연결까지 닫는 것으로 잘못 처리하던 결함을 수정했습니다. SQLite 연결 컨텍스트는 커밋/롤백만 수행합니다. 열린 복구 파일을 `os.replace()`로 교체하면 Windows에서 공유 위반(WinError 32)이 발생할 수 있습니다. 수정 버전은 백업·무결성 검사 뒤 연결을 닫은 다음 파일을 교체하며, 데이터 읽기·검증과 이전 사본 연결도 닫습니다.

이전의 단일 오류 문구만으로 이미 발생한 노트북 예외를 확정할 수는 없습니다. 업데이트 후 문제가 계속되면 다음 **코드와 단계**, 터미널의 숫자 `errno/winerror`로 구분합니다. 설정·비밀번호·키·토큰·자료 본문을 공유하지 마세요.

| 코드 | 의미 |
| --- | --- |
| `SQLITE_BACKUP/recovery_copy` | SQLite 백업 API 또는 사본 무결성 검사 실패 |
| `FILE_WRITE/recovery_copy` | 복구 폴더 생성·권한 설정·파일 교체 실패. WinError 32라면 파일 잠금 확인 |
| `SQLITE_READ/dataset_read` | 작업 사본의 데이터 읽기 실패 |
| `JSON_SERIALIZE/fingerprint` 또는 `metadata_write` | 지문/메타데이터 JSON 직렬화 실패 |
| `FILE_WRITE/metadata_write` | 복구 메타데이터 파일 쓰기·교체 실패 |
| `DATA_VALIDATION/validation` | 필수값·자료형·참조·크기 등 유효성 검사 실패 |

터미널 로거 `reviewlab.cloud.preflight`는 코드·단계·임의 요청 ID·숫자 오류 코드만 기록합니다. 예외 원문, traceback, 파일 경로, 사용자 자료나 인증 정보는 기록하지 않습니다. JSON 메타데이터 작성 전 실패했다면 SQLite 후보 파일만 `cloud/.../pending/<요청 ID>.sqlite3`에 남을 수 있습니다. 기존 파일을 일괄 삭제하지 마세요. 복구 파일 생성 자체가 실패하면 입력을 먼저 복사한 뒤 새로고침하세요.

새 ‘서버 전송 전 중단’ 오류는 해당 요청에서 commit RPC를 호출하지 않았다는 뜻입니다. 반면 서버 전송 뒤 응답을 확인하지 못한 요청은 미확인 상태로 유지합니다. 업데이트·재시작·새로고침은 이러한 요청을 자동 전송하지 않습니다. 이미 남은 요청을 다시 처리하려면 내용을 확인한 뒤 기존 수동 재확인 버튼을 이용하세요. SQL 마이그레이션이나 로그인 설정을 다시 할 필요는 없습니다.

Windows에서 비밀값 없이 회귀 검사를 실행할 수 있습니다.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest tests/test_cloud_preflight.py tests/test_cloud_storage.py tests/test_cloud_ui.py -q
```

GitHub **Actions → ReviewLab cloud regression → Run workflow**의 Windows 전체 회귀 검사에 이 검사를 통합했습니다. 개발 환경의 Linux 검사와 Windows 파일 잠금 모사 검사는 통과했지만, Windows 실기/CI 실행 결과는 별도 확인이 필요합니다. PR/main 자동 실행과 별도 Supabase 프로젝트 검증 절차는 [클라우드 테스트 사용법](TESTING.md)을 참고하세요.
