# 3단계 업데이트와 Supabase SQL v2 적용

이 문서는 **이미 v1 공용 작업공간과 실제 참고문헌 15건을 사용 중인 팀**의 업데이트 안내입니다. 운영 DB에 SQL을 자동 실행하지 않습니다. 개발자가 사용자 운영 DB에 접속하거나 자료 15건을 직접 확인한 것은 아닙니다.

## 적용 전 확인

1. 두 컴퓨터의 입력 작업을 마치고 미확인 저장 요청을 먼저 확인합니다. 결과를 모르는 요청을 자동 재전송하지 마세요. 기존 pending/백업 파일은 삭제하지 않습니다.
2. 현재 앱 **공용 DB 관리**에서 actual/example 각각 전체 SQLite 사본을 다운로드하고, 참고문헌·리뷰 전용 CSV도 별도로 보관합니다. 현재 자료 수·검증 이력·리뷰 프로젝트 수와 작업공간 ID를 기록합니다. Supabase 제공 프로젝트 백업이 사용 가능하면 관리자 정책에 따라 추가 확보합니다.
3. 먼저 **운영과 다른 테스트 Supabase 프로젝트**에 v1 SQL → 새 v2 SQL 순서로 적용하고 가상 자료로 확인합니다. 기존 자동 테스트는 이 순서를 임시 PostgreSQL에서 실행하지만 실제 Supabase Auth/API 설정을 대신하지 않습니다.
4. SQL 파일의 변경 내용을 검토한 뒤 프로젝트 관리자가 운영 적용을 승인해야 합니다. 이 개발 작업에서는 승인받거나 운영 SQL을 실행하지 않았습니다.

## 승인 후 관리자 적용 순서

1. 노트북·데스크탑의 ReviewLab을 모두 종료합니다. 명령 창에서 Ctrl+C를 누릅니다.
2. 이미 v1이 설치된 프로젝트에는 **v1 SQL을 다시 실행하지 않습니다.** Supabase SQL Editor에서 버전을 먼저 확인합니다.

```sql
select version, applied_at from reviewlab.schema_migrations order by version;
```

3. 버전이 1인 프로젝트에 새 파일 [`202610250002_surveys.sql`](migrations/202610250002_surveys.sql)을 전체 선택하여 **한 번** 실행합니다. BEGIN/COMMIT 하나의 트랜잭션이며 v1이 아니면 중단됩니다. 새 프로젝트라면 v1 파일부터 적용합니다.
4. 다시 조회하여 1, 2가 있는지 확인합니다. 설문 테이블 6개와 v2 RPC, RLS·복합 FK·UNIQUE 제약이 추가됩니다. 기존 11개 업무 테이블의 자료를 UPDATE/DELETE/TRUNCATE하지 않습니다. Auth 사용자·작업공간·기존 revision·receipt도 유지합니다.
5. **두 컴퓨터 모두** 최신 GitHub ZIP을 새 폴더에 압축 해제합니다. 기존 폴더/백업을 유지하고 `.streamlit/secrets.toml`만 새 폴더의 같은 위치로 안전하게 복사합니다. 코드나 비밀값을 공유 채팅에 올리지 마세요. `Start_ReviewLab.cmd`를 실행하거나 아래 명령을 사용합니다.

```powershell
$env:PYTHONUTF8 = "1"
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

새 폴더에 `.venv`가 없으면 먼저 `py -3.12 -m venv .venv`를 실행하거나 간편 실행 파일을 이용합니다. 같은 계정·같은 작업공간·같은 데이터 모드를 선택합니다. 프로젝트/작업공간을 새로 만들거나 기존 참고문헌을 다시 이전하지 않습니다.

6. 기존 참고문헌 15건과 검증 기록·리뷰를 확인하고, **예시·연습 자료**에서 가상 설문 CSV를 먼저 테스트합니다. 노트북 업로드 후 데스크탑의 **공용 자료 새로고침**으로 같은 설문이 보이는지 확인합니다.

## 버전 호환과 예상 영향

클라우드 v2는 `workspaces_v2/read_v2/status_v2/commit_v2` RPC를 사용합니다. 기존 v1 조회는 schema_version=2를 알리고 v1 commit은 `RL_SCHEMA_UPGRADE_REQUIRED`로 거부합니다. 구버전 앱이 설문을 빠뜨린 전체 데이터셋을 저장해 설문을 지우는 상황을 방지하기 위한 의도적인 차단입니다. 구버전 클라이언트를 계속 사용하거나 v1 SQL을 다시 적용하면 안 됩니다.

현재 모드 전체 CAS·멱등 요청 ID·권한 검사·미확인 요청 보존 정책을 유지합니다. 설문 answer도 전체 20MB/50,000레코드 한도에 포함됩니다. 예를 들어 100문항×500응답은 답변만 50,000개이므로 실제 공용 업로드 한도는 이보다 작습니다. 클라이언트 사전 검사에서 한도 초과를 거부하며 오프라인 자동 대체 저장을 하지 않습니다.

SQLite는 별도 **스키마 3**입니다. 기존 로컬 v1/v2 DB는 처음 열 때 `backups/before-change-...sqlite3`를 만든 다음 새 테이블을 트랜잭션으로 추가합니다. 백업 실패나 DDL 실패면 중단합니다. 신규 빈 DB에는 불필요한 이전 사본을 만들지 않습니다. 앱 재실행 시 같은 마이그레이션을 반복하지 않습니다.

## 복구와 롤백

SQL 실행 중 실패하면 전체 SQL 트랜잭션을 롤백한 뒤 버전을 조회합니다. 오류 원문에 키나 사용자 자료가 포함되지 않도록 공유를 주의하세요. 테이블을 삭제해서 해결하지 않습니다.

SQL v2 적용 후에는 **v1 앱으로 운영 저장을 재개할 수 없습니다**. 설문 데이터 보호 차단이 작동하기 때문입니다. 문제 발생 시 앱을 중지하고 현재 데이터·pending·전체 백업을 보존한 뒤 v2 호환 수정 버전으로 복구합니다. 설문 테이블 DROP이나 이전 RPC 재활성화를 자동 롤백으로 제공하지 않습니다.

로컬에서 이전 버전을 검토해야 한다면 현재 DB를 교체하지 말고, 이전 전 사본을 별도 데이터 루트의 같은 actual/example 폴더에 `reviewlab.sqlite3`로 복사하여 구버전 앱을 실행하세요. 그 사본에는 이후 설문 입력이 없으므로 원본과 신규 백업도 반드시 유지합니다. 운영 Supabase를 과거 시점으로 되돌리는 작업은 최신 데이터 손실 가능성이 있어 관리자가 별도 복구 계획과 사용자 확인 후 수행해야 합니다.

실제 Supabase/Windows 실기 적용은 이번 개발 환경에서 미검증입니다. SQL 파일만 작성·임시 PostgreSQL에서 검증했으며 운영 적용 여부를 대신 확인하지 않습니다.
